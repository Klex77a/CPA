# Защита Midnight Commit за 5 минут

Источник тайминга — Guide, стр. 4: интерфейс и диалог — 1 минута; оценка, доказательства и N/A — 2 минуты; апелляция — 1 минута; изменение критерия — 1 минута. Это сценарий репетиции. Прохождение в настоящем браузере с секундомером нужно проверить отдельно: программные проверки DOM и API не подтверждают визуальную готовность выступления.

## Подготовка до выступления

1. Откройте уже запущенный сервер на `http://127.0.0.1:3000`. Если страница работает, второй `node server.js` не нужен. Проверьте название реального провайдера и модели в боковой панели. Демо-режим по правилам подходит для репетиции интерфейса; он не подтверждает качество ИИ.
2. Для упражнений используйте синтетический набор `SAMPLE` или отдельную группу `DEMO_DEFENSE`. Для отдельной группы в разделе **«Диалоги»** заполните **«ID для загрузки»**, нажмите **«Импорт JSON»** и выберите [public/demo-sample.json](../public/demo-sample.json). У файла четыре придуманных диалога RU/KZ/EN и пример звонка. Его аудиоссылка `example.com` — заглушка; для прослушивания выберите настоящий доступный звонок из DEV.
3. Выберите исходный чек-лист, откройте `sample-ru-001` и заранее нажмите **«Запустить оценку»**. Проверьте восемь критериев, причины N/A и ссылки на реплики. Не начинайте выступление с ожидания пакетной оценки. Запишите ID выбранной сохранённой оценки.
4. Заранее создайте рабочую копию чек-листа: **«Чек-лист» → «Название»** — `Проверка жюри` → **«Сохранить как новый»**. Для первых четырёх минут снова выберите исходный чек-лист. Последнее упражнение выполняйте в копии. Сохранение исходного чек-листа повысит его версию и сделает прежние DEV-оценки архивными.
5. Подготовьте вкладки **«Диалоги»**, карточку выбранного синтетического разговора и **«Апелляции»**. Нужны сохранённые реальные результаты, а не скриншот успеха. Перед показом проверьте текущее значение критерия: повторная репетиция могла уже изменить его через апелляцию.
6. Перед защитой откройте отчёт [BENCHMARK.md](BENCHMARK.md) и фактически полученный `output/benchmark/latest.json`, если запуск уже завершён. Возьмите из отчёта число кейсов, модель, соглашение с эталоном и ошибки. Синтетические инженерные примеры не являются независимой экспертной оценкой DEV.

## 0:00–1:00 — интерфейс и выбранный диалог

**Действия.** Откройте **«Диалоги»**, покажите выбор набора и чек-листа, фильтры языка/канала и статус оценки. Откройте `sample-ru-001` из подготовленной синтетической группы. Слева находится **«Транскрипт»**, справа — **«Оценка по критериям»**.

**Текст.** «Мы оцениваем работу живого оператора. Бот и системные сообщения сохраняются как контекст. Для каждого критерия есть значение, обоснование и проверяемые реплики. Настройки чек-листа меняются через интерфейс».

**Что подтвердить.** На карточке видны язык RU, исходные роли и провайдер/модель. Приветствие бота в реплике №1 не заменяет приветствие оператора в №4. Нумерация включает все исходные сообщения.

## 1:00–3:00 — объяснение, доказательства и N/A

**1:00–1:40.** Откройте **«Установление контакта»**, прочитайте обоснование и нажмите ссылку на реплику №4: оператор поздоровался, представился и признал неудобство клиента. Текст должен выделиться в транскрипте.

**1:40–2:15.** Покажите **«Идентификация»** и последовательность: просьба назвать кодовое слово → ответ клиента → системное подтверждение → раскрытие баланса. На реальном звонке при доступной записи можно показать переход к приблизительному месту аудио. Не называйте вычисленный таймкод точной разметкой аудио.

**2:15–2:45.** Покажите N/A по **«Выявление потребности»**, если именно так оценён выбранный прогон: в исходном обращении уже указаны баланс и задержка вывода. Ненужный уточняющий вопрос не требуется ради балла. Откройте **«Расчёт и параметры оценки»** и покажите исключение веса N/A из знаменателя.

**2:45–3:00.** Покажите предупреждение по непроверенным фактическим утверждениям консультации. «Без базы знаний мы не выдаём заявленный оператором банковский срок за проверенный факт. Результат проверяется человеком». Если подготовленный прогон получил `needs_review`, покажите это состояние и причину; не представляйте его как успешно проверенный.

### Проверенный числовой пример для репетиции

В предыдущей проверке API на синтетическом `QA_20261107 / sample-ru-001` сохранён прогон DeepSeek: `c01=YES`, `c02=NA`, `c03=YES`, `c04=20`, `c05=YES`, `c06=10`, `c07=YES`, `c08=NO`. Применимый вес — `100 − 15 = 85`; набрано 85; исходный итог — **100**. Учебное решение проверяющего `c04: 20 → 15` уменьшает набранный вес на 5: `100 × 80 / 85 = 94,12`. Исходная оценка ИИ остаётся 100.

Это проверка арифметики и истории решений на одном придуманном разговоре. Новый запуск модели может дать другой ответ; репетируйте по фактически сохранённому результату. Учебное снижение балла не доказывает ошибку оператора и не является независимой экспертной разметкой.

## 3:00–4:00 — апелляция и решение проверяющего

**3:00–3:20.** В выбранном критерии нажмите **«Оспорить»**, напишите комментарий с номером реплики и нажмите **«Отправить»**. Пример учебного комментария: «Проверка сценария апелляции: прошу пересмотреть полноту ответа в реплике №8». Появляется статус ожидания решения.

**3:20–3:45.** Откройте **«Апелляции»**, найдите нужный диалог и критерий. Покажите исходное значение и фрагмент разговора. В блоке **«Решение проверяющего»** введите причину. Для учебной демонстрации арифметики выберите 15 вместо 20 и нажмите **«Изменить оценку»**. Ясно назовите это учебным решением. На реальной оценке причиной должны быть факты разговора и правило чек-листа.

**3:45–4:00.** Вернитесь в карточку. Покажите исходный и финальный итог, причину, автора и историю решения. Для приведённого числового примера ожидается **100 → 94,12**. Если критерий уже равен 15 после предыдущей репетиции, повторное решение 15 не изменит итог: сначала подготовьте отдельную синтетическую оценку либо покажите уже сохранённый переход. Не очищайте реальные DEV-результаты ради демонстрации.

## 4:00–5:00 — изменение критерия через настройки

**4:00–4:20.** Откройте **«Чек-лист»**, в **«Открыть чек-лист»** выберите подготовленную копию `Проверка жюри`. В поле **«Формулировка / правило оценки (её читает ИИ)»** измените правило завершения. Учебный пример: «Да — оператор подвёл итог И попрощался. Одного предложения дальнейшей помощи недостаточно». Сохраните кнопкой **«Сохранить (новая версия)»**. Покажите увеличение номера версии.

**4:20–4:45.** Вернитесь в синтетический диалог, выберите эту копию в **«Чек-лист для оценки»** и нажмите **«Запустить оценку»**. В разговоре есть предложение помощи и прощание; явное резюме в последней реплике отсутствует. Модель должна применить изменённое определение. Сохранённая оценка исходного чек-листа остаётся в **«История оценок»**.

**4:45–5:00.** Покажите номер версии нового результата и обоснование изменённого критерия. Если запрос ещё выполняется, покажите выполнение и сохранённую историю; не объявляйте неполученный ответ успешным. Завершите: «Новый критерий применяется из настроек; исходные оценки и решения проверяющего сохраняются».

## Файлы и доказательства для вопросов после защиты

- [results/dev/results.json](../results/dev/results.json) — реальные 65 DEV-записей после подготовки и проверки. В `team_name` должно быть `Midnight Commit`. Путь к файлу сам по себе не подтверждает его наличие, актуальность или push.
- `results/prod/results.json` — только после получения фактического контрольного набора из 10 диалогов. Имя группы задают организаторы; оно может отличаться от `PROD`.
- [ACCEPTANCE.md](ACCEPTANCE.md) — внутренняя инженерная рубрика, а не официальные баллы жюри.
- [BENCHMARK.md](BENCHMARK.md) и фактический отчёт запуска — измеренное сравнение с синтетическим эталоном, со знаменателями и ограничениями.
- В официальной выгрузке `needs_review` остаётся записью `status:"error"` без балла до проверки человеком. Новый спорный анализ не подменяется старым `ok`. Сетевой сбой без нового анализа сохраняет доступность последнего готового результата.

Финальная проверка выполняется до дедлайна: `npm.cmd run check`, `npm.cmd test`, проверка каждого JSON с исходным набором через `scripts/validate-results.js`, затем commit и push обязательных файлов. Сам сценарий не выполняет эти действия и не подтверждает отправку в Git.
