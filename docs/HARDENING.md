# Доработки после строгого ревью

Дата: 8 ноября 2026 года. Отчёт описывает реализованные изменения и границы проверки. Оценка «100/100», независимая точность и завершённая визуальная приёмка не заявляются.

Финальный `npm test` прошёл полностью: 24 серверных набора и 59 React-тестов. Также прошли проверка 58 JavaScript-файлов, строгий TypeScript, форматирование и native Vercel dry-run: 93 файла, 2 284 923 байта, без приватных пакетов и секретов.

## Рабочий процесс

- Контроллер очереди перенесён в WorkspaceProvider. Карточка, аналитика и апелляции больше не останавливают следующие шаги. Общая панель показывает прогресс, ошибки, известные расходы и отмену. Завершённую панель можно скрыть без удаления задания.
- Последняя актуальная ошибка попытки сохраняется в списке после перезагрузки. Предыдущая хорошая оценка остаётся видна; новый успех убирает устаревшую ошибку. Есть фильтр ошибок и явный повтор.
- Карточка обновляет текущий результат после очереди, сохраняя аудио, позицию и поиск. Исторический результат остаётся закреплённым. Сбой обновления сводки не превращает уже полученный ответ оценки в визуальный неуспех.
- Список и карточка используют общую идемпотентную отправку. После потери ответа сохраняются исходные `request_id`, тело и `force`; проверка исхода не создаёт новую платную попытку. Автоматического повтора POST нет. Неопределённый исход требует отдельного действия пользователя с предупреждением о возможном предыдущем списании.

## Хранение и расходы

Платный запрос вынесен из транзакции: короткий claim → внешняя модель → короткий commit в свежий snapshot. Пока модель отвечает, можно рассматривать другую апелляцию, редактировать или отменять очередь. Дубликаты объединяются, а повторная фиксация не повторяет вызов модели. Изменение входов при том же ключе операции возвращает понятный конфликт.

Lease переживает смену экземпляра функции. Если процесс исчез после внешнего запроса, результат оплаты может быть неизвестен; автоматического повторного списания приложение не инициирует. Гарантии exactly-once у внешнего провайдера нет. Локальный `/evaluate` также поддерживает ключ операции.

Отсутствующий usage больше не считается нулевым счётом. Полные `usage`/`cost_usd` при неполных данных равны `null`; известные части сохраняются в `known_usage`/`known_cost_usd`. Очередь, аналитика, карточка, CLI и benchmark различают полный итог и нижнюю границу по доступным данным. Это расчёт по настроенным ценам, не счёт провайдера.

## Реальная проверка PostgreSQL

[Сохранённый отчёт](qa-results/cloud-concurrency.json) получен на подключённом Neon с синтетическим отложенным оценщиком: конкурентная запись — 884 мс, отмена — 882 мс; обе завершились до освобождения оценщика. Два синтетических расчёта, **ноль запросов провайдеру**. Уникальный временный workspace удалён, отсутствие записи проверено. Production-диалоги и оценки не менялись. SHA-256 в отчёте относятся к локальным байтам файлов на Windows в момент проверки.

Воспроизводимая команда по умолчанию не читает конфигурацию и не использует сеть:

```sh
node scripts/check-cloud-concurrency.js
```

Для разрешённой реальной БД явно указываются `--live --database-config <закрытый-файл>`. Файл должен содержать DATABASE_URL или совместимую переменную; другие значения скрипт не использует. Не добавляйте его в Git. Не применяйте Node-флаг `--env-file`: он может загрузить все переменные до входа в скрипт. Отчёт через `--out` разрешён только внутри `output/private/`.

## Контроль модели

Исторические 15 примеров, их отчёты и DEV JSON сохранены. Добавлен отдельный challenge: 39 синтетических диалогов, 312 меток, по 13 RU/KZ/EN; промежуточные оценки, N/A, идентификация, три типа critical на каждом языке и длинные искусственные транскрипты. Эталон заморожен до первого вызова модели.

Первый разрешённый живой прогон: **283/312 совпадений (90,71%)**, 38 обработанных диалогов, один технический сбой; 21 диалог совпал полностью. Среди заложенных нарушений: TP=9, FP=0, FN=0, unknown=1 на отрицательном случае. Эти числа относятся к конкретным инженерным меткам, не к независимой точности продукта.

После просмотра исходных реплик инженерное ревью признало **21 метку в 17 диалогах спорной**: 9 сомнительных эталонов, 10 пограничных трактовок, 2 риска объяснения модели. Это последующий внутренний разбор; новые правильные ответы им не устанавливаются. Исходные метки и предсказания не подгонялись. Интерфейс показывает предупреждение «Эталон требует проверки» рядом с сырым процентом согласия.

- [Первоначальный отчёт без изменений](benchmark-results/challenge-baseline.json).
- [Текущий отчёт с явно описанной поправкой только учёта расходов](benchmark-results/challenge-latest.json).
- [Разбор спорных меток](benchmark-results/challenge-review.json).

Один сбой сохранил 85 мс, один HTTP-запрос и общий код. Это не доказательство таймаута. Старый runner записал синтетические нули usage/cost; поправка заменяет их на неизвестные и явно ссылается на оригинал. Доступная расчётная стоимость — $0,138576 по 38 попыткам, стоимость одной попытки неизвестна. Ответы, итоговые баллы, время, статусы и 283/312 сохранены. Новых запросов для этой поправки не выполнялось.

Readiness отдельно показывает семантические измерения и параметры запуска. CLI-прогон не подтверждает задержку и устойчивость опубликованного HTTP/Vercel-пути. Фраза о ещё не выполненном запуске в замороженных ограничениях fixture относится к моменту создания набора; фактический запуск определяется датой отчёта и его статусом.
