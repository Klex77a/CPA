# Проверка качества RU / KZ / EN

`test/fixtures/benchmark-cases.json` содержит 15 синтетических диалогов: по пять на русском, казахском и английском. Для каждого заранее указаны все восемь ответов, краткое основание по действующему чек-листу и ссылки на исходные реплики. Это **engineering reference**, составленный командой реализации, а не независимая экспертная разметка. Полученный процент нельзя представлять как точность на DEV/PROD, оценку жюри или доказательство качества на всех реальных обращениях.

Метки фиксируются до запуска модели. Если обнаружена ошибка разметки, нужно описать причину, изменить версию набора и выполнить новый прогон. Исправлять эталон ради совпадения с текущим ответом модели нельзя. Старый отчёт сохраняют отдельно для сравнения. Апелляции не улучшают измерение: сравниваются исходные `criteria` и `original_result`.

## Наблюдённые результаты 7 ноября 2026 года

Сохранены два реальных запуска `deepseek / deepseek-flash`: [исходный отчёт](benchmark-results/baseline.json), промпт `2026-11-07.6`, и [повторный отчёт](benchmark-results/latest.json), промпт `2026-11-07.7`. В обоих случаях использованы те же 15 диалогов, те же 120 меток и тот же SHA-256 набора: `1a36ffc9a14e2511137003b3ce3e8a8f16ce9e44eeb3e4e06b27ab577e9de0cf`. После просмотра первого результата промпт был уточнён, затем выполнен второй запуск. Это измерение разработки и регрессии **на том же наборе**, а не независимая контрольная выборка. Метки между запусками не менялись.

- Точные совпадения по критериям: **117/120 (97,50%) → 119/120 (99,17%)**. Полностью совпавшие диалоги: **12/15 → 14/15**. В обоих запусках получены 15 валидных результатов, нет failed/invalid, структурная проверка доказательств пройдена для всех 120 критериев.
- По языкам: RU **39/40 → 40/40**, KZ **40/40 → 40/40**, EN **38/40 → 39/40**. Все расхождения относятся к ведению диалога `c06`: **12/15 → 14/15**; остальные семь критериев совпали в обоих запусках по 15/15.
- Критические нарушения в обоих запусках: TP=2, TN=13, FP=0, FN=0, unknown=0; precision=2/2, recall=2/2. Для N/A: TP=27, TN=33, FP=0, FN=0, unknown=0 по 60 допустимым позициям. Два положительных примера critical недостаточны для общего вывода о надёжности обнаружения нарушений.
- Средняя абсолютная ошибка итогового балла уменьшилась **с 1,298 до 0,75 балла** по всем 15 диалогам. Максимальная ошибка при этом выросла **с 6,93 до 11,25 балла**: оставшееся расхождение стало сильнее. Арифметика сохранённых итогов согласована с ответами модели в обоих запусках.
- Время одной оценки: p50 **7,543 → 7,657 с**, p95 **13,018 → 18,351 с**; наблюдены все 15 времён в каждом запуске. Параллелизм — 2, независимых samples — 1. Один прогон и 15 коротких случаев не дают надёжного прогноза задержки на больших реальных обращениях.
- Наблюдаемая приблизительная стоимость: **$0,043691 → $0,046211** за 15 диалогов; во втором запуске в среднем **$0,003081 за диалог**. Выполнено соответственно **15 и 16 HTTP-попыток**; доступные токены повторов включены. Всего два запуска — около **$0,089902**. Расчёт использует настройки этих запусков: $0,30 за миллион входных и $1,20 за миллион выходных/мыслительных токенов; это оценка по конфигурации, а не подтверждённый счёт провайдера или обещание будущей цены.

Оставшееся расхождение — `en-missing-discovery-no-answer`, критерий `c06`: эталон **10**, модель **4**. В реплике 1 клиент не назвал два сравниваемых типа заявок; оператор отказался отвечать без уточнения, а в реплике 3 клиент указал именно на пропущенный уточняющий вопрос. Обоснование модели трактует это как вынужденный переспрос и резкий обрыв словом `Goodbye`. Эталон отделяет отсутствие выявления потребности (`c02=false`), отсутствие ответа (`c04=0`) и неполное завершение (`c07=false`) от ясности формулировок: непонятных формулировок, вызвавших переспрос, здесь нет. Из-за выбора 4 вместо 10 итог модели равен **20,00**, эталонный — **31,25**. Исходные реплики, обоснование и ссылки сохранены в повторном отчёте; спор оставлен видимым, эталон под ответ модели не изменялся.

Наблюдённое улучшение относится к этому небольшому инженерному набору и одному повторному запуску после изменения промпта. Оно не доказывает улучшение на скрытых данных, статистическую устойчивость, независимую экспертную точность либо качество на DEV/PROD. Следующий шаг для такой проверки — отдельный заранее закрытый и независимо размеченный набор.

Проверка набора без API, ключей и расходования средств:

```powershell
node scripts/benchmark.js
node test/benchmark.test.js
```

Явно разрешённый платный запуск по настройкам `.env`:

```powershell
node scripts/benchmark.js --live --out output/benchmark/latest.json --concurrency 2
```

Флаг `--live` и путь `--out` обязательны одновременно. `mock` запрещён. Параллелизм ограничен одним или двумя диалогами. Настройка `SAMPLES`, повторные HTTP-попытки и исправления не отключаются: измеряется фактический производственный режим. Файл отчёта сохраняется даже при несовпадении, ошибке API или ответе `INVALID`.

Коды завершения: `0` — все 120 ответов совпали и все результаты валидны; `1` — отчёт сохранён, есть несовпадения/невалидность/ошибки; `2` — ошибка запуска, конфигурации или входного файла. `output/` уже исключён из Git. Для доказательства качества на защите следует сохранить конкретный проверенный отчёт вместе с версией кода, а не запускать модель заново во время выступления.

Отчёт содержит дату, модель, провайдера, версию промпта, настройки оценки, версию и SHA-256 чек-листа и эталонного набора. Для каждого случая сохраняются исходные синтетические реплики, ожидаемые/полученные ответы, расхождения, реальное обоснование модели, ссылки/цитаты, причина N/A, непроверенные утверждения и проверка доказательств. Номера в отчёте начинаются с **1** и включают клиента, оператора, бота и систему. Ключи API, URL с учётными данными и сырые тела ошибок провайдера в отчёт не копируются.

Метрики интерпретируются отдельно:

- `criterion_match.rate` — точные совпадения / все 120 ожидаемых ответов. Каждый пропущенный или неудачный диалог сохраняет восемь строк в знаменателе. `valid_only_rate` — дополнительная условная метрика с явно указанным числом допустимых ответов; она не заменяет основную.
- `by_language` и `by_criterion` показывают те же числитель и знаменатель отдельно. `cases.exact` считает полное совпадение значений, а `cases.fully_valid_exact` дополнительно требует валидности результата и доказательств. `completed`, `invalid` и `failed` разделены.
- `critical` — TP/TN/FP/FN и `unknown`; `precision = TP / (TP + FP)`, `recall = TP / число всех эталонных critical=true`. Неудачный критический случай остаётся в знаменателе recall и отдельно попадает в `unknown_positive`. При нулевом знаменателе метрика равна `null`, а не 100%.
- `na` — такая же матрица для четырёх критериев, где N/A разрешён. Положительный класс — N/A. `INVALID` учитывается как неизвестный ответ, а не как N/A.
- `final_score` — средняя и максимальная абсолютная ошибка итогового балла. Итог независимо пересчитывается из полученных ответов с исходными весами и исключением N/A. Число сравнимых и отсутствующих итогов явно указано; неудачный вызов не подменяется нулевой ошибкой. Отдельно считается несоответствие сохранённого итога арифметике ответов.
- `evidence` проверяет существование реплик, вхождение цитат, границы/порядок участков, наличие объяснения и причины N/A. Это проверка привязки доказательств к источнику; смысловую убедительность обоснования дополнительно оценивает человек.
- `timing` показывает наблюдённое время, p50/p95 и покрытие; `cost` — наблюдаемую приблизительную стоимость, количество случаев с известной/неизвестной стоимостью. Метрики не обещают точный биллинг провайдера. После ошибки учитываются доступные токены и стоимость уже выполненных попыток, если адаптер вернул эти сведения.

Покрытие классов записано в `dataset.label_distribution`. Текущий набор проверяет приветствие/имя первого оператора отдельно от бота, язык приветствия, уточнение до ответа и его отсутствие, подтверждённую идентификацию и защищённое действие без неё, полный ответ и отсутствие ответа, шаблонную/конкретную эмпатию, паузу без предупреждения, переспрос из-за формулировок, варианты завершения и технический обрыв, частную платную услугу, оскорбление и инструкцию клиента, выдающую себя за системную.

Ограничения существенны: только 15 коротких чатов; discovery и identification имеют лишь по одному положительному и отрицательному примеру. Нет консультаций на ступени 5/10/15, ступени dialogue=0, консультации N/A, голоса/аудио, проверки реальных тарифов и регламентов. Разница между языками по пяти случаям нестабильна. Для заявления о качестве на реальных данных нужен отдельный закрытый набор, размеченный независимыми предметными экспертами, с разрешением расхождений и достаточным покрытием всех классов. Этот набор служит воспроизводимой инженерной проверкой известных правил и регрессий.

Повторный расчёт метрик без API из заранее сохранённых исходных оценок:

```powershell
node scripts/benchmark.js --from output/benchmark/outcomes.json --out output/benchmark/replay.json
```

Вход — массив `{ "case_id": "ru-complete-summary", "evaluation": { ... } }` либо объект `{ "outcomes": [...] }`. Для неудачи используется `{ "case_id": "...", "error": { "code": "TIMEOUT" }, "duration_ms": 123, "cost_usd": null }`; допустимы доступные `usage` и `timing`. Пропущенные случаи явно становятся ошибками, неизвестные/дублирующиеся ID отклоняются. Идентичность модели в таком отчёте берётся из входных оценок и помечается как непроверенная. Сам агрегированный отчёт не является исходной оценкой для `--from`.
