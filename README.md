# Midnight Commit · Freedom CQA

Прототип для хакатона Freedom Broker. ИИ предлагает предварительную оценку работы оператора по настраиваемому чек-листу: баллы, объяснения и реплики-доказательства. Пользователь может оспорить отдельный критерий. Проверяющий подтверждает или меняет его с причиной; система пересчитывает итог и сохраняет историю.

Обязательная экспертная комиссия, независимая разметка и ручное утверждение каждой оценки не требуются. Проверяющий — действие в сценарии апелляции; на демонстрации его выполняют в интерфейсе без отдельной регистрации.

Уточнение организаторов от 8 ноября: главный ориентир отбора топ-50 — близость автоматических оценок десяти новых контрольных диалогов к их Ground Truth. Дополнительно учитываются функциональность, удобство, корректность обработки новых входов и разнообразие архитектур. Для звонков письменные критерии адаптируются к устной речи; система должна поддерживать различные чек-листы. Эти требования и границы текущей реализации зафиксированы в [ТЗ](docs/REQUIREMENTS.md) и [критериях приёмки](docs/ACCEPTANCE.md). Собственный benchmark не является оценкой по скрытому эталону организаторов.

Оценщик `2026-11-08.1` разделяет канальный контекст и правила выбранного чек-листа: ID критериев не задают их смысл, шкалы и N/A берутся из конфигурации. Для звонка анализируется транскрипт; дикция и темп без передачи аудио не оцениваются. Явный недостаток обязательных данных помечается как непроверяемый ответ, а не подменяется максимальным баллом или N/A. [Устройство и проверка оценщика](docs/EVALUATOR.md). Исторические benchmark-отчёты описывают прежний промпт; сами по себе они не измеряют новую версию.

Облачная версия: **https://midnight-commit-cqa.vercel.app**. Вход — по логину и паролю команды; настройка и результаты проверки опубликованной версии описаны в [VERCEL.md](docs/VERCEL.md).

Документация: [полное ТЗ](docs/REQUIREMENTS.md), [критерии приёмки](docs/ACCEPTANCE.md), [технический аудит](docs/AUDIT.md). Внутренняя рубрика не является официальной формулой жюри.

Последнее ревью и работа над замечаниями жюри: [отчёт](docs/CODE_REVIEW.md). Предыдущая проверка сайта: [QA-отчёт](docs/QA_REPORT.md). При изменении транскрипта или чек-листа прежний результат помечается архивным; новая оценка сохраняет исходный текст для доказательств.

После ревью добавлены общая очередь на всех экранах, сохраняемые причины ошибок и короткие облачные транзакции вокруг запроса к ИИ. Синтетические benchmark и [инструменты ручной разметки](docs/QUALITY_REVIEW.md) относятся к дополнительным инженерным исследованиям. Они не входят в обязательный пользовательский маршрут, не блокируют оценки или сдачу результатов и не заменяют апелляции.

Итоги этих доработок, реальный PostgreSQL-прогон, первый живой challenge и оставшиеся ограничения: [HARDENING.md](docs/HARDENING.md).

## Быстрый запуск

Нужен **Node.js 22.12+**, рекомендуется Node.js 24. Интерфейс написан на React и TypeScript, сборка — Vite.

Для облачной версии на **Vercel** подготовлены постоянное Postgres-хранилище, закрытый доступ и сохраняемые пакетные задания. Инструкция: [VERCEL.md](docs/VERCEL.md). Vercel устанавливает PostgreSQL-драйвер из `package-lock.json`; локальный JSON-режим его не использует. Конфигурация деплоя сама по себе не означает, что сайт уже опубликован.

```bash
git clone https://github.com/Klex77a/CPA.git
cd CPA
cp .env.example .env        # Windows: copy .env.example .env; только если .env ещё не существует
# откройте .env и вставьте DEEPSEEK_API_KEY и DATA_API_URL
npm ci
npm start
```

Откройте **http://127.0.0.1:3000**. По умолчанию сервер слушает только этот компьютер (`HOST=127.0.0.1`).

`npm start` сначала собирает интерфейс в `dist/`, затем запускает сервер. Для разработки откройте два терминала: `npm run dev:api` и `npm run dev`. Адрес интерфейса с быстрым обновлением — **http://127.0.0.1:5173**; `/api` перенаправляется на локальный сервер. Если PowerShell блокирует `npm.ps1`, используйте `npm.cmd`.

* Без ключа ИИ система запускается в **ДЕМО-режиме** (оценка по ключевым словам), чтобы проверить интерфейс.
* Для проверки без настройки нажмите **«Открыть пример · 4 диалога»**, затем **«Оценить весь набор»**. Эти примеры не заменяют DEV65/PROD10 и не подтверждают точность ИИ.
* Ключ DeepSeek: https://platform.deepseek.com → «API keys».
* Тесты расчёта баллов: `node test/scoring.test.js`.

## Как пользоваться (сценарий защиты)

1. **Диалоги** → введите `DEV` → **«Получить из API»**. Загрузятся 65 диалогов организаторов.
   *Если API недоступен,* нажмите **«Импорт JSON»** и выберите сохранённый ответ API (или `data/sample/SAMPLE.json`).
2. Выберите чек-лист → **«Оценить весь набор»** (или «Оценить» в строке диалога).
3. Нажмите на строку → **карточка диалога**: слева транскрипт, справа итог, секции и критерии. Нажатие на доказательство прокручивает к реплике и подсвечивает её; у звонков запись перематывается на это место.
4. У любого критерия → **«Оспорить»** → комментарий → «Отправить».
5. **Апелляции** → проверяющий видит спорную оценку, комментарий и фрагмент диалога → «Подтвердить» или «Изменить» с причиной. Итог пересчитывается, в карточке видны исходная оценка, решение и финальный результат.
6. **Чек-лист** → измените/замените критерий → «Сохранить (новая версия)» → **Диалоги** → «Оценить все». Оценки по старой версии сохраняются для сравнения.
7. **Контрольный набор:** введите `group_id`, который сообщат организаторы → «Получить» → «Оценить все».

## Официальная сдача JSON

CSV подходит для анализа. Приложение к гайду требует `results/dev/results.json` на **65** записей и `results/prod/results.json` на **10** контрольных чатов.

На контрольный набор отводится **один час целиком: получение, оценка, проверка и commit/push до стоп-кода**. Пошаговые команды и проверка отправки: [инструкция контрольного часа](docs/SUBMISSION.md). CI проверяет DEV и, когда появится файл, PROD; локально полноту ID и границы доказательств нужно сверять с исходными данными.

В списке диалогов нажмите **«Результаты JSON»**, укажите **Midnight Commit** и выберите DEV/PROD. Сохраните скачанный файл в соответствующую папку. Экспорт проверяет восемь исходных определений, веса, шкалы, N/A, баллы и доказательства; несовместимый изменённый чек-лист допускается к оценке/CSV, но не выдаётся за официальный. Для экспериментов удобно создавать копию исходного чек-листа.

Для уже сохранённых оценок файл можно подготовить из терминала:

```sh
npm run prepare:results -- --split=dev --dry-run
npm run prepare:results -- --split=dev
npm run prepare:results -- --split=prod --group=CONTROL_GROUP
```

DEV по умолчанию берётся из группы `DEV`. Команда не вызывает модель: сохраняет результаты настоящих оценок и ошибки в установленные пути. PROD подготавливается после получения контрольного набора. По умолчанию название команды — **Midnight Commit**.

На каждый исходный ID получается одна запись, включая ошибки: `status: "error"`, `criteria: []`, `score: null` и причина. Неудачные вызовы сохраняются отдельно с фактически запрошенной моделью. Необработанные диалоги не скрываются, ошибка не заменяется нулём. Демо-эвристика не допускается к сдаче как модель. Без единого результата или попытки настоящей модели JSON для сдачи не создаётся.

`evidence_turns` нумеруются **с 1 по всем исходным репликам**, включая бота/систему. `dialogue: 7` означает исходную ступень 7/10, до веса 15. `critical_flag` не обнуляет итог.

```sh
node scripts/validate-results.js results/dev/results.json --split=dev --source=data/datasets/DEV.json
node scripts/validate-results.js results/prod/results.json --split=prod --source=data/datasets/CONTROL_GROUP.json
```

Замените `CONTROL_GROUP` фактическим ID. `--split` обязателен; `--source` дополнительно проверяет полноту исходных ID и границы реплик. Проверьте количество ошибок обработки. Оба файла должны попасть в **commit и push** до стоп-кода; экспорт не публикует их автоматически. Реальные файлы не подменяются вымышленными результатами.

## Дополнительные возможности

- **Аналитика качества.** Средний балл и медиана, распределение баллов, сравнение по языкам и каналам, грубые нарушения, апелляции, стоимость оценки. Блок «Главное» формулирует выводы автоматически.
- **Тепловая карта «Где операторы теряют баллы».** Процент выполнения каждого критерия в целом и по языкам RU, KZ и EN. Сразу видно, чему обучать операторов.
- **Рейтинг операторов.** ИИ извлекает имя оператора из приветствия. Для каждого оператора видны средний балл, число диалогов, языки, грубые нарушения и самый слабый критерий.
- **Рекомендации оператору.** В каждой карточке 1–3 конкретных совета по этому диалогу со ссылкой на реплику.
- **Зона риска.** Диалоги с грубыми нарушениями и самые низкие оценки, с переходом в карточку в один клик.
- **Уверенность ИИ.** При голосовании (`SAMPLES=3`) у каждого критерия видно согласие прогонов, а спорные ответы выносятся на дашборд.

## Как считается балл

Расчёт делает **код** (`src/scoring.js`), а не ИИ. Модель только выбирает допустимый ответ по каждому критерию. Одна и та же функция считает первичный результат и результат после апелляции.

- «Да» = полный вес, «Нет» = 0. Шкала: `вес × ступень / максимальная ступень шкалы` (7 из 10 при весе 15 → 10,5).
- N/A исключает критерий из числителя и знаменателя: `итог = 100 × набрано / вес применимых`.
- Промежуточные значения не округляются, округляется только показ. Пример: 30,5 / 65 → 46,923… → **46,92**, хотя показанные доли 15,38 + 15,38 + 16,15 дают 46,91. В карточке есть подсказка с формулой.
- Если нет применимых критериев с весом или у критерия нет допустимого ответа, итог не рассчитывается (вместо 0 или 100 показывается «—»).
- Грубая ошибка — отдельный флаг, итог она не обнуляет.
- Пользовательская шкала проверяется при сохранении: ступени конечные, неотрицательные, без повторов, максимум больше 0.

## Проверка ответа модели

1. В запрос передаётся сохранённая конфигурация чек-листа: определения, допустимые ответы, шкалы, условия N/A. Ответ запрашивается строго по JSON Schema (`responseJsonSchema` у Gemini). Если API схему не примет, система продолжит работу без неё, а серверная проверка останется.
2. Сервер проверяет: каждый критерий оценён ровно один раз; нет неизвестных критериев; ответ допустим для типа критерия; N/A разрешён и имеет причину и контекст; ступень принадлежит шкале; ID реплик существуют (`m0…mN`); фрагмент цитаты действительно входит в реплику; у диапазона начало не позже конца; основания есть; объяснения не скопированы между критериями.
3. При ошибках модель получает **один** повторный запрос с их перечнем (`REPAIR_ATTEMPTS`). Если ответ и после этого не проходит проверку, результат помечается **«требует проверки человеком»**, а критерий без допустимого ответа не получает баллов.
4. Транскрипт — недоверенные данные: он передаётся внутри `<transcript>`, и попытки «закрыть» этот блок из реплики нейтрализуются.

**Доказательства** бывают трёх видов: конкретные реплики, участок «действие ожидалось, но отсутствует» и проверенный участок (например, «проверен весь диалог» для «грубых ошибок нет»). Текст цитаты берётся из исходного транскрипта по ID.

**Фактическая корректность.** Базы знаний компании в проекте нет. Модель не должна объявлять путь, срок или тариф правильными только потому, что их назвал оператор. Непроверяемые утверждения выводятся отдельной пометкой «нужна проверка человеком» и сами по себе не дают «Нет», 0 или N/A.

**Итоговый вывод** собирается из результатов критериев, поэтому не может им противоречить. **Рекомендации** привязаны к критериям: «требование чек-листа» допускается только для невыполненного критерия, всё остальное — «совет».

## Кэш и повторная оценка

Ключ результата включает: транскрипт, содержимое и версию чек-листа, провайдера, модель, значимые настройки и версию инструкций (`PROMPT_VERSION`). Изменение любого критерия даёт новый ключ, и запрос уходит в модель. «Оценить все» пропускает только диалоги с готовым результатом для того же ключа; «переоценить заново» и кнопка «Переоценить» в карточке всегда делают новый запрос и не затирают прежний результат. Одинаковые одновременные запросы объединяются.

## Время и настройки модели

В карточке видны общее время, время запросов к модели, число запросов (включая повтор после проверки), число HTTP-попыток, ожидание перед повторами, время в очереди и токены (включая токены «размышления»). Ключ API передаётся в заголовке и в журнал не пишется.

| Переменная `.env` | По умолчанию | Назначение |
|---|---|---|
| `LLM_TIMEOUT_MS` | 240000 | тайм-аут одного запроса |
| `LLM_MAX_ATTEMPTS` | 3 | попыток при 429/5xx/тайм-ауте (учитывается `retryDelay`) |
| `REPAIR_ATTEMPTS` | 1 | повторных запросов при невалидном ответе |
| `CONCURRENCY` | 2 | параллельных диалогов в пакетной оценке |
| `TEMPERATURE` | не задана | для Gemini 3 не передаётся: Google рекомендует значение по умолчанию 1.0 |
| `GEMINI_THINKING_LEVEL` | не задан | `low` / `medium` / `high`; не задан — значение модели |
| `DEEPSEEK_REASONING_EFFORT` | не задан | `none` / `low` / `high` / `max`; не задан — значение API (размышление включено) |
| `SAMPLES` | 1 | прогонов с голосованием |

Они не заменяют визуальную проверку размеров, прокрутки и печати в настоящем браузере. Для автоформатирования исходников интерфейса выполните `npm run format:web`.

GitHub Actions настроен на Windows и Ubuntu / Node.js 24: синтаксис, тесты, контрольная разметка и схема сохранённого DEV. Ключ API не требуется. Фактический результат удалённого CI будет доступен после публикации изменений. Используются официальные [checkout](https://github.com/actions/checkout) и [setup-node](https://github.com/actions/setup-node).

## Архитектура


**Хранение:** JSON-файлы в `data/`. Для продакшена заменяется на Dataverse/БД без изменения интерфейса.

**Языки:** один чек-лист для RU, KZ и EN; модель определяет язык клиента по репликам, объяснения пишет на русском. Реплики бота и системные события передаются как контекст и не засчитываются как действия оператора.

**CORS:** данные организаторов запрашивает сервер. Произвольным сторонним сайтам доступ к локальным диалогам запрещён. Для доверенного отдельного HTML-компонента настройте точные `CORS_ORIGINS`.

**Локальный MVP:** JSON-хранилище рассчитано на один процесс; локальная очередь находится в памяти и не переживает перезапуск. **На Vercel:** состояние и прогресс хранятся в Postgres, доступ требует пароль команды. Модель вызывается вне блокировки рабочего пространства. Очередь продолжает работу при переходах между экранами, пока открыта вкладка приложения. После закрытия следующие шаги ожидают восстановления клиента. Неопределённая попытка после гибели функции требует явного повтора; гарантии единственного списания у внешнего провайдера не заявляются. Для большой нагрузки нужны фоновые workers и более детальная модель хранения.

Проверка DNS/IP аудиоссылок блокирует закрытые сети; запрос закрепляется на проверенном адресе с обычной TLS-проверкой, HTML ограничен 2 МБ/20 секундами. Дополнительно можно задать точные `AUDIO_ALLOWED_HOSTS` страницы записи и CDN. Перенаправления страницы записи запрещены; сервису с редиректом потребуется конечный URL или переход к исходному плееру. Позиции звука приблизительны; дикция/интонация по тексту не оцениваются.

## Модель и стоимость

По умолчанию **DeepSeek** (`deepseek-flash`, облачный API). Все критерии оцениваются в одном запросе; при невалидном ответе делается не больше одного повторного запроса.

### Как повышается точность
1. **Уточнённые правила критериев.** В `src/default-checklist.json` к формулировкам из PDF добавлены разборы спорных случаев со стр. 3 («Нет» против N/A, что считать первым ответом, когда нужна идентификация).
2. **Факты, вычисленные кодом.** Наличие события закрытия чата, первая и последняя реплики оператора.
3. **Строгая проверка ответа** (см. выше) и один повторный запрос при ошибках. Скрытые рассуждения модели не запрашиваются и не показываются.
4. **Голосование (self-consistency).** При `SAMPLES=3` каждый диалог оценивается тремя независимыми прогонами. По каждому критерию берётся ответ большинства, для шкалы — медиана. В карточке видно согласие прогонов (например, «согласие 2/3»), то есть уверенность модели.
5. **Детерминированный расчёт.** Баллы, N/A и округление считает код.

Примерный расход на один прогон: около 3–4 тыс. входных токенов и около 1–2 тыс. выходных. При цене `deepseek-flash` в часы пик ($0.30 / $1.20 за 1 млн токенов) это **около $0.002–0.004 за прогон** без учёта токенов размышления (при `SAMPLES=3` — в 3 раза больше). Токены размышления оплачиваются как выходные. Стоимость каждой оценки показывается в карточке; она считается по ценам часа пик без скидки за кэш, поэтому реальный счёт может быть ниже.

Модель меняется в `.env` (`LLM_PROVIDER`, `LLM_MODEL`).
